# 使用说明

## 第一次启动

双击工程内的 Start.bat。内置方案为“MiniGame 开发”，根目录为 E:\MiniGame，包含 MiniGame、AssetRuntime、CommonResource、Source、SandboxEngine、AIGamePlay、RainbowEngine、Editor 共 8 个仓库。

主窗口顶部显示当前方案、根目录和分支组。中部左侧是仓库树，右侧显示当前选中仓库的完整目录、远端、分支、检测时间和处理原因。底部可以切换执行计划与运行日志。

启动时并行扫描本地状态；不会自动同步或自动运行环境准备。

## 保存多套方案

点击“管理方案”：

- 新建：从默认 8 仓库模板创建一套方案。
- 复制：复制当前方案，获得独立的名称、目录、分支和仓库配置。
- 删除：移除方案记录，保留至少一套方案。
- 选择目录：修改工程根目录，也可以手动输入尚不存在的绝对路径。
- 添加仓库、移除所选配置：编辑仓库条目。
- 导入方案文件：用文件中的全部方案替换当前编辑内容；点击保存才会写入应用配置。
- 导出全部方案：导出当前编辑器内的全部方案。

删除方案或仓库条目只操作配置，不删除本地文件。取消关闭对话框会放弃本次编辑。

仓库表中的“相对目录”以工程根目录为起点；主仓库填点号。仓库 ID 用于配置关联，应保持唯一。分支组与固定分支只能选一个：例如填 game、清空固定分支，或者清空分支组、填写 release/my-branch。

“启用”决定加载方案时是否默认勾选，不表示禁止手动同步。“环境必需”决定构建环境准备的前置检查；一项都不选时使用全部启用仓库。“排序参考”使用逗号分隔的仓库 ID，仅影响列表展示顺序；旧配置中的 depends_on 继续兼容。仓库树按目录层级展示，不代表同步必须等待父仓库。

仓库名称右侧的“忽略修改提醒”和“强制更新（不备份）”分别控制提醒和同步方式，支持随方案复制、保存、导入和导出；旧配置和新建仓库默认都不勾选。

分支组在顶部按“名称=分支”的格式编辑，每行一组。主窗口顶部也可直接改分支并保存。仓库详情中的“读取远端分支”读取远端列表，选择后修改该仓库的分支组或固定分支；共享分支组的仓库会一起变化。

## 检查与同步

“检查状态”检查选中的仓库。已有仓库会 fetch 目标分支，用新的远端引用计算领先/落后；尚未克隆的仓库用 ls-remote 确认分支。该操作不切换本地分支，不修改工作区文件。

启动扫描和“检查状态”最多同时检查 8 个仓库，完成一个就更新对应行，无需等待其他仓库。底部显示“已完成 / 总数”和处理中数量，日志仍按仓库归属过滤。多个 worktree 如果共用同一个 Git 目录，其远端检查会依次执行，避免同时更新共享引用。

“同步所选”会重新检查，所以可以直接点击。只将明确选中的仓库加入队列，按配置列表顺序逐个执行；每项根据自身状态决定操作：

1. 不存在或空目录：验证分支后，完整克隆指定单分支。
2. 已有仓库：验证目录自身就是工作树根目录，核对 origin、工作区及目标分支。
3. 必要时切换目标分支，再进行 fast-forward-only 更新。
4. 写入独立结果和日志，继续下一仓库。

只选子仓库时，不会自动检查父仓库的同步状态，也不会自动勾选、克隆或更新父仓库。即使父仓库有修改、目标分支不存在或同步失败，选中的子仓库仍会自行检查和同步。例如 Source 有本地修改时，RainbowEngine 仍可快进更新。父目录不存在时，克隆子仓库只创建必要目录，不创建父 Git 仓库。

目录布局冲突、真正的 Git 子模块、仓库自身的修改或分叉仍按各自规则处理。这些状态属于该仓库自身的检查结果，不再显示“前置仓库未完成”。自动准备构建环境仍需全部“环境必需”仓库就绪，这不会阻止前面的独立同步。

“同步此仓库”针对右侧当前选中的仓库。“重试失败”重新检查上次失败或待处理条目。每次重试都按真实目录状态决定操作。

并行只用于独立的状态检查任务。同步按配置列表顺序逐个执行，前一仓库的失败不阻止后续仓库；文件 Discard 在其独立流程中执行。

## 初始化加速

新建工作目录时，可以复用本机已有工程（例如 D:\MiniGame、D:\AIMiniGame、D:\MiniGameProfiler）里的 Git 对象和 LFS 大文件，只从远端补齐目标分支缺少的数据。只对“未克隆 / 空目录”的仓库生效；已有仓库照常获取、切换、快进。

**设置。** “管理方案”中的“初始化加速”区域随方案保存、复制、导入和导出：

| 项目 | 说明 |
|---|---|
| 初始化方式 | 自动复用本地工程：按来源顺序为每个仓库挑选可用来源。指定源工程：只用第一个来源目录，或仓库行里的“初始化来源”。纯网络下载：与原来的克隆完全相同。 |
| 本地工程来源 | 工程根目录，每行一个，越靠前越优先；“添加来源”可以选择目录。 |
| 复用 Git 数据 / 复用 LFS 大文件 | 可分别关闭。 |
| 无法复用时 | 回退远端下载（默认）；或停止该仓库，此时找不到可用 Git 来源的仓库不会下载。 |
| 初始化来源（可选，仓库表最后一列） | 为单个仓库指定源仓库目录，例如 D:\AIMiniGame\AssetRuntime。指定目录无效时按“无法复用时”处理，“指定源工程”方式下不会改用其他工程。 |

新建的方案默认使用“自动复用本地工程”，并预填本机存在的上述三个目录；升级前已保存的方案保持“纯网络下载”，需要时打开设置、选择方式后保存。

**先看计划。** 勾选仓库后点击“初始化计划”，或在“管理方案”中点击“扫描本地工程”。两者只读取本地信息，不访问远端、不改源工程。每个仓库会列出：

- 目标目录、目标分支和当前状态；已有仓库注明“沿用现有同步规则”。
- 选中的 Git 来源、其他可用来源、可提供 LFS 对象的目录。
- 未采用的目录及原因：目录不存在、没有 .git、此目录的 .git 无效（Git 向上识别到了父仓库）、远端与配置不同、浅克隆、部分克隆、对象库正在维护等。
- 预计执行方式；LFS 需要和命中的对象数在同步取得目标提交后统计。
- 以前中断遗留的 .repotool-init-* 临时目录，可确认无程序使用后手动删除。

来源按仓库远端身份匹配，不看文件夹名称：SSH 与 HTTPS 地址只有主机和仓库路径相同时才视为同一仓库。源仓库处于其他分支、有未提交修改或本地提交都不影响复用，这些内容也不会进入新工程。浅克隆不能提供 Git 数据，但它已下载的 LFS 对象仍可按哈希复用。

**执行。** 点击“同步所选”。运行日志按“检查来源 → 复用 Git 数据 → 复用 LFS → 下载缺失数据 → 检出 → 验证完成”输出阶段：

1. 在目标旁边的临时目录中，借用源仓库对象、从原始远端克隆目标分支，暂不检出；完成后解除对源仓库的依赖。
2. 按目标提交列出 LFS 对象，从来源复制并逐个校验哈希后放入新仓库自己的 LFS 存储；校验不通过的对象不使用。
3. 仍缺少的 LFS 对象从原始 LFS 服务下载，然后检出文件。
4. 核对分支、提交、origin 和对象独立性，再把临时目录改名为目标目录。

结果说明写明 Git 来源、LFS 需要 / 已有 / 本地复制（字节数）/ 下载的数量和目标提交；运行记录 JSON 的 details 字段保存各阶段耗时和全部候选来源。仍有 LFS 文件未填充时结果为“待处理”，不会标成完成。

初始化加速不会覆盖已有工程：如果在就位前目标目录被其他操作写入内容，该仓库报告“已被其他操作占用”，保留对方文件。失败或中断时只删除本次创建的临时目录。远端认证失败或分支不存在直接报告；Git 数据阶段的其他失败在“回退远端下载”时改用一次普通网络克隆。完成后源工程被删除或清理，不影响新工程。

目前不包含 UGit/LFS 缓存服务、P2P 下载、Setup 依赖包复用和整目录复制；这些属于[初始化加速方案](initialization-acceleration-plan.md)中的后续阶段。

## 按仓库忽略提醒与强制更新

在“管理方案与仓库”中找到目标行，勾选名称右侧的选项并保存。两个选项相互独立：

| 选项 | 作用 |
|---|---|
| 忽略修改提醒 | 不显示橙色“有本地修改”，改为灰色“修改提醒已忽略”；详情不自动展开修改文件列表。点击“文件改动 / Discard”仍能查看完整文件状态和 Diff。 |
| 强制更新（不备份） | 在你点击同步时，先核对远端和分支，再丢弃未提交文件修改并按原有分支规则更新；整个流程不保存文件备份或 stash。 |

只勾选“忽略修改提醒”不会允许覆盖文件。普通同步仍会检查真实工作区状态；分叉、认证失败、远端不一致等其他提示照常显示。该选项只影响所配置仓库的显示，父仓库记录的子模块指针变化仍由父仓库自己的策略处理。

强制更新会丢弃该仓库普通文件的暂存和未暂存改动，恢复已跟踪文件；已暂存新增文件和普通未跟踪文件会被移除。不清理被 Git 忽略的文件、配置中的独立子仓库或子模块，也不递归删除目录。暂存删除路径上若仍有被忽略的文件，则阻止更新并保留它。链接、冲突或其他无法按普通文件处理的状态也会停止，避免处理到子仓库或目录。

本地提交会保留，仍使用快进更新；本地与远端分叉时停止，不把目标分支重置到远端。远端不存在、认证失败、目标目录布局冲突，或目标分支被其他 worktree 使用时，会在丢弃之前停止。执行中途发生错误或中断时可能已经丢弃部分文件，运行日志记录实际进度，不承诺回滚。

只有明确选中的仓库可以执行强制丢弃。“同步此仓库”视为明确选择该仓库；同步不会自动加入其他仓库。“重试失败”只重试上次的失败或待处理条目，其中开启强制更新的仓库必须仍处于勾选状态。

保存配置、启动扫描和“检查状态”都不会丢弃文件。“执行计划”与右侧详情会标明强制更新不备份；不再另行弹出 Discard 备份确认框。需要保留备份时，使用独立的“文件改动 / Discard”中的“备份并丢弃所选”，该功能的备份行为保持不变。

## Windows 原生右键菜单

在仓库列表中的某一行右键，打开该仓库目录的 Windows Shell 菜单，与在资源管理器中进入该目录后右键空白区域对应。菜单可包含本机安装的 Git、TortoiseGit 等扩展，具体项目取决于本机配置。

- 菜单作用于右键所在行；原有仓库勾选不变，不会一次操作所有已勾选仓库。
- 正在检查、同步或执行其他任务时，先等待任务结束再打开菜单。目录尚未创建或右键落在空白区域时不弹出菜单。
- 菜单打开期间暂停工具内的其他任务入口；取消菜单不扫描，执行菜单命令后自动重新读取所有仓库的本地状态。
- 如果菜单打开了外部程序，它可能在菜单关闭后继续工作。外部操作结束后再点“检查状态”，即可更新最终结果。
- 菜单命令由 Windows 和外部扩展负责执行。需要工具提供的备份式 Discard 时，仍使用“文件改动 / Discard”；外部菜单操作不生成这里的 Discard 备份。

## 各状态如何处理

| 状态 | 含义与处理 |
|---|---|
| 空目录 / 未克隆 | 可同步，空目录无需手动删除。 |
| 目录被占用 | 非空且不是该目录自身的 Git 仓库；检查路径和内容，再更换路径或自行整理。 |
| 仓库不完整 | 没有有效 HEAD，常见于初始化或克隆中断；保留现场，人工处理后重新检查。 |
| 有本地修改 | 打开“文件改动 / Discard”查看文件和 Diff；需要保留的改动在自己的 Git 工作流中保存，需要放弃的文件可勾选后备份并丢弃，再重试。 |
| 本地领先 | 本地提交已保留，工具不会推送。 |
| 待快进更新 | 可以直接同步到更新的远端提交。 |
| 分支已分叉 | 本地和远端都有独立提交；手动决定如何整理后重试。 |
| 分离 HEAD | 先保存相关提交，并在外部 Git 工具中选择本地分支。 |
| Git 操作未完成 | 完成或自行中止正在进行的 merge、rebase 等操作。 |
| 远端不一致 | 编辑配置中的远端，或点击“采用实际 origin”更新配置；程序不自动更换仓库的 origin。 |
| 目录布局冲突 | 父仓库目标提交在子仓库路径放了文件或目录，或把其祖先变成文件/链接/gitlink；先调整配置或仓库布局。父仓库在子仓库路径本身登记 gitlink 不算冲突。 |
| Git 子模块 | 只剩两种情况：子仓库路径位于另一个 gitlink 之内；或该目录由父仓库用 git submodule 初始化（.git 是指向父仓库的文件）。后者可以打开“文件改动 / Discard”处理内部文件；如需按分支独立更新，删除该目录后由工具重新克隆。 |

**父仓库把子仓库路径登记为 gitlink 时。** 例如 Source 在某些分支把 Core/RainbowEngine 记为 gitlink（有无 .gitmodules 均可），AssetRuntime 把 CommonResource 记为子模块。只要该路径是方案里配置的仓库，工具就按配置的分支独立克隆、切换和快进，不修改父仓库记录的 gitlink 提交；父仓库也不会因此显示“有本地修改”或“目录布局冲突”，强制更新父仓库时不会动子仓库。父仓库自己暂存的 gitlink 改动仍会显示。
| 认证失败 | 检查系统 Git 的 SSH 密钥或凭据管理器，完成认证后重试。 |
| 目标分支不存在 | 核对分支拼写或用“读取远端分支”重新选择。 |

如果 Git 报告某个 ignored 文件会被覆盖，程序会保留文件并失败退出；先决定如何保留这些本地文件，再重试。工具不改写 .gitignore，也不把父仓库自己的已跟踪改动当作子仓库噪声忽略。

## 文件改动与 Discard

1. 在主窗口选中仓库，点击右侧“文件改动 / Discard”，或直接双击仓库。
2. 查看列表中的文件路径、类型、已暂存状态和未暂存状态。单击行选择预览对象，勾选框用于选择要丢弃的文件，两者相互独立。
3. 双击文件或点击“查看 Diff”。已跟踪文件分别显示 HEAD 到暂存区、暂存区到工作区的差异；未跟踪文本文件预览内容，二进制文件显示说明。很大的 Diff/文本只截取预览，备份仍保存完整字节。
4. 勾选不再需要的文件，点击“备份并丢弃所选（Discard）”。确认框显示仓库、当前提交与项数；展开详细信息可核对全部路径。取消不会执行丢弃。
5. 确认后先备份，再重新校验当前提交、所选文件和暂存状态，最后执行丢弃。完成后自动刷新文件列表；关闭对话框后，主窗口会重新扫描所有仓库的本地状态。

| 文件类型 | Discard 的结果 |
|---|---|
| 已跟踪文件的修改 | 恢复到当前 HEAD；该文件的暂存和未暂存改动都会被丢弃。 |
| 已跟踪文件的删除 | 恢复当前 HEAD 中的文件。 |
| 已暂存的新增文件 | 恢复为当前 HEAD 的状态；HEAD 中没有的新增文件会被移除。 |
| 重命名 | 原路径和新路径一起恢复；如果原路径又出现内容，则拒绝操作，避免隐含覆盖。 |
| 未跟踪文件 | 备份后从工作区删除；不会递归删除目录。 |
| 子模块提交指针、嵌套仓库 | 不可勾选；在方案中配置过的子仓库可点击“进入子仓库”，处理内部文件。 |
| 冲突、未完成的 Git 操作、链接或暂不支持的索引状态 | 只展示和预览，并说明不可丢弃原因；先用外部 Git 工具处理。 |

例如 AssetRuntime 列表显示 CommonResource 为子模块时，选中该行并点击“进入子仓库”，就能查看 CommonResource 中真正修改的文件。Source 中的 AIGamePlay 同理。也可以直接在主窗口选中 CommonResource/AIGamePlay 打开文件改动。只处理内部文件不会改变子模块 HEAD；如果它与父仓库记录的提交不同，父仓库仍可能显示“有本地修改”。

文件列表按 Git 状态显示，不列出被忽略且未跟踪的文件。默认不勾选任何文件；“全选可丢弃文件”也会排除受保护条目。这个操作不提供按 Diff 行丢弃或“只丢弃未暂存部分”的模式，请在确认前核对两个 Diff 区域。

备份位于配置目录的 discard-backups 子目录，默认是：

~~~text
%LOCALAPPDATA%\MiniGameRepoTool\discard-backups\<时间-编号>\
  worktree\       丢弃前实际存在的工作区文件，按原相对路径保存
  staged.patch    所选文件的完整暂存改动，支持二进制文件
  manifest.json  原 HEAD、所选路径、原先是否存在、校验值与执行结果
  RECOVERY.md    恢复说明
~~~

完成或部分失败后可点击“打开上次备份”。目前没有一键恢复按钮；需要恢复时，先保留现在的新改动，再依据 RECOVERY.md 确认仍在原 HEAD、相关路径的暂存区符合补丁基线。若 staged.patch 非空，先将它应用到暂存区，然后把 worktree 中的文件按相对路径复制回原仓库；空补丁可跳过。原先缺失的路径须结合 manifest.json 恢复为缺失状态。不要直接用旧备份覆盖后来产生的新工作。

备份失败或执行前发现文件变化时，不开始丢弃。开始后若遇到文件占用、Git 错误等，界面报告“未全部完成”，保留备份并刷新实际状态；不会声称整批回滚。工具内部通过运行锁避免同一配置目录多实例并发；操作期间应避免在其他 Git 客户端中同时修改同一批文件。

## 停止和中断

“停止队列”不再派发新的仓库。并行检查时，已经开始的检查会完成；同步时，当前仓库操作会完成。长时间 clone/fetch 仍会继续。

“中断当前操作”停止剩余队列，并终止当前任务拥有的全部 Git/SSH 进程树；并行检查时会同时通知所有已开始的检查中断，适合终止长时间网络操作。

已经完成的仓库不会回滚。中断可能留下不完整克隆；再次同步时会重新检查，不自动删除文件，也不承诺续传。窗口关闭时如果任务还在运行，会让用户选择是否中断后退出。

## 编译构建

点击主窗口右下角“编译构建”。窗口沿用当前方案的工程根目录，参数随方案保存、复制、导入和导出；默认只勾选 IB 编译，目标 MiniGame、VS2019、Debug、x64。

1. 勾选要运行的步骤：构建设置、生成 SLN 工程、IncrediBuild 编译。只选一步就只执行该步；多选时按此顺序运行。
2. 修改对应页签中的参数。上方 VS 版本和平台同时用于生成预设与 IB 工程路径；Python 用于设置和生成。
3. 可先点“检查配置”：核对入口与已有 SLN/目标，调用 IB 技能的 ValidateOnly，不运行设置、生成或编译。尚无工程时会提示先生成。
4. 点击“执行所选步骤”。界面逐步显示状态和日志；前一步失败或中断时不继续下一步。
5. “停止后续步骤”等待当前步骤结束；“中断当前步骤”终止本次任务，IB 使用本次独立会话文件调用停止脚本。

构建设置对应 SetupScript/Win_Setup.bat，支持下载设置依赖、生成 WinSetup.zip 或使用离线依赖包。生成对应 Tools/ProjectBat/VS2019_64-MiniGame.bat 的 Python 入口、dev 模式及环境变量，不执行末尾 pause。编译调用 mini-compile-ib 技能的脚本，支持 Build/Rebuild/Clean、配置/平台、目标与 IB 监视器；不会自动从编译回退到工程生成或直接 MSBuild。

手动构建按当前本地源码和工程执行，不要求先同步 Git 或清空本地修改。“管理方案”里的同步后自动准备继续只执行构建设置，且保留全部“环境必需”仓库检查；不会自动生成或编译。实际下载和依赖安装仍由工程自身 SetupWin.py 定义。

完整参数、步骤对应关系、日志位置见[编译构建说明](build.md)。

## 日志和配置恢复

“运行日志”支持全部仓库/选中仓库过滤、复制当前视图与导出。界面保留最近 5000 行；同步和环境准备的完整输出持续写入 runs 目录，导出“全部仓库”时使用完整文件。

每次同步、环境准备或构建有一份 .json 结果和对应 .log 日志。“打开运行记录目录”可直接查看。构建窗口另提供“打开日志目录”，包含 build.log、IB 原始日志与本次 session.json。URL 中常见用户名、密码和 token 参数会在界面日志和结构化运行记录中脱敏。HTTP(S) 地址不要嵌入凭据，使用系统凭据管理器；SSH 地址可以保留 git 用户名。

profiles.json 每次有效保存后会保留旧版本 profiles.json.bak。配置损坏时应用会报错并保留文件；检查 JSON，或用备份恢复后再启动。也可以用独立目录启动应用，再从管理方案导入有效配置文件。

同一配置目录的实例共享任务锁；Git 与构建任务不能同时执行。不同 --data-dir 是隔离的测试/配置空间，不共享这把锁。IB 技能还会检查已有 IB 会话，工具不传 AllowConcurrent。

## 命令行与开发

~~~powershell
# 正常启动
.\.venv\Scripts\python.exe run.py

# 使用另外的配置目录
.\.venv\Scripts\python.exe run.py --data-dir D:\RepoToolProfiles\test --no-scan

# 启动验证与窗口截图，不执行 Git
.\.venv\Scripts\python.exe run.py --smoke-test --data-dir artifacts\smoke-data --screenshot artifacts\main-window.png

# 开发依赖与测试
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
.\.venv\Scripts\python.exe -m pytest -q
~~~
