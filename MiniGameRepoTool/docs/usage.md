# 使用说明

## 第一次启动

双击工程内的 Start.bat。内置方案为“MiniGame 开发”，根目录为 E:\MiniGame，包含 MiniGame、AssetRuntime、CommonResource、Source、SandboxEngine、AIGamePlay、RainbowEngine、Editor 共 8 个仓库。

主窗口顶部显示当前方案、根目录和分支组。中部左侧是仓库树，右侧显示当前选中仓库的完整目录、远端、分支、检测时间和处理原因。底部可以切换执行计划与运行日志。

启动时并行扫描本地状态；不会自动同步或自动运行环境准备。

## 保存多套方案

点击“管理方案”：

- 新建：从默认 8 仓库模板创建一套方案。
- 复制：复制当前方案，获得独立的名称、目录、分支和仓库配置。
- 删除：移除方案记录，保留至少一套方案。
- 选择目录：修改工程根目录，也可以手动输入尚不存在的绝对路径。
- 添加仓库、移除所选配置：编辑仓库条目。
- 导入方案文件：用文件中的全部方案替换当前编辑内容；点击保存才会写入应用配置。
- 导出全部方案：导出当前编辑器内的全部方案。

删除方案或仓库条目只操作配置，不删除本地文件。取消关闭对话框会放弃本次编辑。

仓库表中的“相对目录”以工程根目录为起点；主仓库填点号。仓库 ID 用于依赖关联，应保持唯一。分支组与固定分支只能选一个：例如填 game、清空固定分支，或者清空分支组、填写 release/my-branch。

“启用”决定加载方案时是否默认勾选，不表示禁止手动同步。“环境必需”决定构建环境准备的前置检查；一项都不选时使用全部启用仓库。“额外依赖”使用逗号分隔的仓库 ID；嵌套目录的父子依赖自动推导，不必重复填写。

分支组在顶部按“名称=分支”的格式编辑，每行一组。主窗口顶部也可直接改分支并保存。仓库详情中的“读取远端分支”读取远端列表，选择后修改该仓库的分支组或固定分支；共享分支组的仓库会一起变化。

## 检查与同步

“检查状态”检查选中的仓库。已有仓库会 fetch 目标分支，用新的远端引用计算领先/落后；尚未克隆的仓库用 ls-remote 确认分支。该操作不切换本地分支，不修改工作区文件。

启动扫描和“检查状态”最多同时检查 8 个仓库，完成一个就更新对应行，无需等待其他仓库。底部显示“已完成 / 总数”和处理中数量，日志仍按仓库归属过滤。多个 worktree 如果共用同一个 Git 目录，其远端检查会依次执行，避免同时更新共享引用。

“同步所选”会重新检查，所以可以直接点击。队列按前置仓库到后代的顺序执行：

1. 不存在或空目录：验证分支后，完整克隆指定单分支。
2. 已有仓库：验证目录自身就是工作树根目录，核对 origin、工作区及目标分支。
3. 必要时切换目标分支，再进行 fast-forward-only 更新。
4. 写入独立结果和日志，继续下一仓库。

只选子仓库时，如果父仓库已经在目标分支上且没有阻塞状态，会直接使用父仓库，保留其当前提交；不会因其落后于缓存远端而擅自更新。必要前置仓库缺失或未就绪时会加入队列并显示原因。

“同步此仓库”针对右侧当前选中的仓库。“重试失败”重新检查上次失败或待处理条目。每次重试都按真实目录状态决定操作。

并行只用于独立的状态检查任务。同步仍按依赖顺序逐个执行，文件 Discard 仍在其独立流程中执行。

## Windows 原生右键菜单

在仓库列表中的某一行右键，打开该仓库目录的 Windows Shell 菜单，与在资源管理器中进入该目录后右键空白区域对应。菜单可包含本机安装的 Git、TortoiseGit 等扩展，具体项目取决于本机配置。

- 菜单作用于右键所在行；原有仓库勾选不变，不会一次操作所有已勾选仓库。
- 正在检查、同步或执行其他任务时，先等待任务结束再打开菜单。目录尚未创建或右键落在空白区域时不弹出菜单。
- 菜单打开期间暂停工具内的其他任务入口；取消菜单不扫描，执行菜单命令后自动重新读取所有仓库的本地状态。
- 如果菜单打开了外部程序，它可能在菜单关闭后继续工作。外部操作结束后再点“检查状态”，即可更新最终结果。
- 菜单命令由 Windows 和外部扩展负责执行。需要工具提供的备份式 Discard 时，仍使用“文件改动 / Discard”；外部菜单操作不生成这里的 Discard 备份。

## 各状态如何处理

| 状态 | 含义与处理 |
|---|---|
| 空目录 / 未克隆 | 可同步，空目录无需手动删除。 |
| 目录被占用 | 非空且不是该目录自身的 Git 仓库；检查路径和内容，再更换路径或自行整理。 |
| 仓库不完整 | 没有有效 HEAD，常见于初始化或克隆中断；保留现场，人工处理后重新检查。 |
| 有本地修改 | 打开“文件改动 / Discard”查看文件和 Diff；需要保留的改动在自己的 Git 工作流中保存，需要放弃的文件可勾选后备份并丢弃，再重试。 |
| 本地领先 | 本地提交已保留，工具不会推送。 |
| 待快进更新 | 可以直接同步到更新的远端提交。 |
| 分支已分叉 | 本地和远端都有独立提交；手动决定如何整理后重试。 |
| 分离 HEAD | 先保存相关提交，并在外部 Git 工具中选择本地分支。 |
| Git 操作未完成 | 完成或自行中止正在进行的 merge、rebase 等操作。 |
| 远端不一致 | 编辑配置中的远端，或点击“采用实际 origin”更新配置；程序不自动更换仓库的 origin。 |
| 目录布局冲突 | 父仓库目标提交占用子仓库路径，或把其祖先变成文件/链接；先调整配置或仓库布局。 |
| Git 子模块 | 可以打开“文件改动 / Discard”处理内部普通文件；子模块提交指针仍由父仓库管理，工具不独立克隆、切分支或更新子模块。 |
| 认证失败 | 检查系统 Git 的 SSH 密钥或凭据管理器，完成认证后重试。 |
| 目标分支不存在 | 核对分支拼写或用“读取远端分支”重新选择。 |

如果 Git 报告某个 ignored 文件会被覆盖，程序会保留文件并失败退出；先决定如何保留这些本地文件，再重试。工具不改写 .gitignore，也不把父仓库自己的已跟踪改动当作子仓库噪声忽略。

## 文件改动与 Discard

1. 在主窗口选中仓库，点击右侧“文件改动 / Discard”，或直接双击仓库。
2. 查看列表中的文件路径、类型、已暂存状态和未暂存状态。单击行选择预览对象，勾选框用于选择要丢弃的文件，两者相互独立。
3. 双击文件或点击“查看 Diff”。已跟踪文件分别显示 HEAD 到暂存区、暂存区到工作区的差异；未跟踪文本文件预览内容，二进制文件显示说明。很大的 Diff/文本只截取预览，备份仍保存完整字节。
4. 勾选不再需要的文件，点击“备份并丢弃所选（Discard）”。确认框显示仓库、当前提交与项数；展开详细信息可核对全部路径。取消不会执行丢弃。
5. 确认后先备份，再重新校验当前提交、所选文件和暂存状态，最后执行丢弃。完成后自动刷新文件列表；关闭对话框后，主窗口会重新扫描所有仓库的本地状态。

| 文件类型 | Discard 的结果 |
|---|---|
| 已跟踪文件的修改 | 恢复到当前 HEAD；该文件的暂存和未暂存改动都会被丢弃。 |
| 已跟踪文件的删除 | 恢复当前 HEAD 中的文件。 |
| 已暂存的新增文件 | 恢复为当前 HEAD 的状态；HEAD 中没有的新增文件会被移除。 |
| 重命名 | 原路径和新路径一起恢复；如果原路径又出现内容，则拒绝操作，避免隐含覆盖。 |
| 未跟踪文件 | 备份后从工作区删除；不会递归删除目录。 |
| 子模块提交指针、嵌套仓库 | 不可勾选；在方案中配置过的子仓库可点击“进入子仓库”，处理内部文件。 |
| 冲突、未完成的 Git 操作、链接或暂不支持的索引状态 | 只展示和预览，并说明不可丢弃原因；先用外部 Git 工具处理。 |

例如 AssetRuntime 列表显示 CommonResource 为子模块时，选中该行并点击“进入子仓库”，就能查看 CommonResource 中真正修改的文件。Source 中的 AIGamePlay 同理。也可以直接在主窗口选中 CommonResource/AIGamePlay 打开文件改动。只处理内部文件不会改变子模块 HEAD；如果它与父仓库记录的提交不同，父仓库仍可能显示“有本地修改”。

文件列表按 Git 状态显示，不列出被忽略且未跟踪的文件。默认不勾选任何文件；“全选可丢弃文件”也会排除受保护条目。这个操作不提供按 Diff 行丢弃或“只丢弃未暂存部分”的模式，请在确认前核对两个 Diff 区域。

备份位于配置目录的 discard-backups 子目录，默认是：

~~~text
%LOCALAPPDATA%\MiniGameRepoTool\discard-backups\<时间-编号>\
  worktree\       丢弃前实际存在的工作区文件，按原相对路径保存
  staged.patch    所选文件的完整暂存改动，支持二进制文件
  manifest.json  原 HEAD、所选路径、原先是否存在、校验值与执行结果
  RECOVERY.md    恢复说明
~~~

完成或部分失败后可点击“打开上次备份”。目前没有一键恢复按钮；需要恢复时，先保留现在的新改动，再依据 RECOVERY.md 确认仍在原 HEAD、相关路径的暂存区符合补丁基线。若 staged.patch 非空，先将它应用到暂存区，然后把 worktree 中的文件按相对路径复制回原仓库；空补丁可跳过。原先缺失的路径须结合 manifest.json 恢复为缺失状态。不要直接用旧备份覆盖后来产生的新工作。

备份失败或执行前发现文件变化时，不开始丢弃。开始后若遇到文件占用、Git 错误等，界面报告“未全部完成”，保留备份并刷新实际状态；不会声称整批回滚。工具内部通过运行锁避免同一配置目录多实例并发；操作期间应避免在其他 Git 客户端中同时修改同一批文件。

## 停止和中断

“停止队列”不再派发新的仓库。并行检查时，已经开始的检查会完成；同步时，当前仓库操作会完成。长时间 clone/fetch 仍会继续。

“中断当前操作”停止剩余队列，并终止当前任务拥有的全部 Git/SSH 进程树；并行检查时会同时通知所有已开始的检查中断，适合终止长时间网络操作。

已经完成的仓库不会回滚。中断可能留下不完整克隆；再次同步时会重新检查，不自动删除文件，也不承诺续传。窗口关闭时如果任务还在运行，会让用户选择是否中断后退出。

## 准备构建环境

按钮“准备构建环境”独立于 Git 同步，也可在方案中勾选自动准备。执行前会检查全部“环境必需”仓库，而不仅是这一次选中的仓库。

步骤如下：

1. 确认 Tools/Setup/SetupWin.py 存在。
2. 如果 Tools/buildtools/Python39/python.exe 缺失，使用 Tools/7z.exe 解压 Tools/buildtools/Python39.zip。
3. 在工程根目录启动仓库自带的 Python，执行 SetupWin.py；实时显示脚本输出。
4. 使用解压与 Python 的实际退出码报告成功或失败。

工具直接执行这两步，没有调用 Win_Setup.bat。这与批处理先从 SetupScript 执行 pushd .. 后的工作目录一致。准备失败不会覆盖仓库同步成功记录，可以单独重试准备。

实际下载、依赖安装等行为由工程自身 SetupWin.py 定义。

## 日志和配置恢复

“运行日志”支持全部仓库/选中仓库过滤、复制当前视图与导出。界面保留最近 5000 行；同步和环境准备的完整输出持续写入 runs 目录，导出“全部仓库”时使用完整文件。

每次同步或环境准备有一份 .json 结果和对应 .log 日志。“打开运行记录目录”可直接查看。URL 中常见用户名、密码和 token 参数会在界面日志和结构化运行记录中脱敏。HTTP(S) 地址不要嵌入凭据，使用系统凭据管理器；SSH 地址可以保留 git 用户名。

profiles.json 每次有效保存后会保留旧版本 profiles.json.bak。配置损坏时应用会报错并保留文件；检查 JSON，或用备份恢复后再启动。也可以用独立目录启动应用，再从管理方案导入有效配置文件。

同一配置目录的实例共享任务锁；任务运行时另一个实例无法开始 Git 任务。不同 --data-dir 是隔离的测试/配置空间，不共享这把锁。

## 命令行与开发

~~~powershell
# 正常启动
.\.venv\Scripts\python.exe run.py

# 使用另外的配置目录
.\.venv\Scripts\python.exe run.py --data-dir D:\RepoToolProfiles\test --no-scan

# 启动验证与窗口截图，不执行 Git
.\.venv\Scripts\python.exe run.py --smoke-test --data-dir artifacts\smoke-data --screenshot artifacts\main-window.png

# 开发依赖与测试
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
.\.venv\Scripts\python.exe -m pytest -q
~~~

第一版以本地和映射到本机的 Windows 工程目录为目标，没有图形冲突解决、内嵌 Git 终端、自动定时同步或独立 exe 发布包。历史记录通过日志目录查看。
