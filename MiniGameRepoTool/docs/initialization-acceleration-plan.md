# MiniGame 工程初始化加速方案

日期：2026-09-30。状态：第一版已实现（见文末“第一版实现情况”）；第二阶段及后续可选项尚未实现。适用工程：`D:\git\Tools\MiniGameRepoTool`。

本方案整理了 UGit 缓存与 D 盘已有工程的复用方式，用于减少新建 MiniGame 工作目录时的重复下载。编写方案时仅形成文档，没有执行真实工程的复制、克隆、拉取或缓存配置修改。

**建议采用的方式是：优先复用本地仓库的 Git 对象和 LFS 大文件，再从远端补齐目标分支所缺的数据。** UGit 加速作为可选下载通道；完整复制工程作为后续高级模式。每个仓库独立选择来源，某个仓库失败不阻止其他所选仓库，不增加“等待前置仓库完成”的条件。

**已核实的本机情况。** 以下结果来自本次讨论中的只读检查，是检查时的状态；正式执行前仍需重新验证。

| 检查对象 | 已观察到的情况 | 对方案的影响 |
|---|---|---|
| UGit | 已安装 5.54.0，存在 `UGit-p2p` 组件 | 可以提供安装检测；组件存在不代表对应仓库能使用加速服务 |
| `D:\MiniGame` | 主仓库、Source、SandboxEngine、AIGamePlay、RainbowEngine 可识别为独立仓库 | 可作为多个仓库的候选来源 |
| `D:\MiniGame\AssetRuntime` | `.git` 中仅观察到 `objects` 目录；Git 向上识别到了主工程根目录 | 不能作为有效的 AssetRuntime 源仓库 |
| `D:\AIMiniGame` | 识别到主仓库、AssetRuntime、Source、SandboxEngine、RainbowEngine | 可补充另一套工程中不可用的来源 |
| `D:\MiniGameProfiler` | 识别到主仓库、AssetRuntime、CommonResource、Source、SandboxEngine、RainbowEngine | 可作为候选来源；CommonResource 是浅克隆，不能直接按完整 reference 仓库处理 |
| 本地 LFS 数据 | `D:\MiniGame` 与其 Source 仓库的 `.git/lfs/objects` 中存在对象文件 | 具备按目标对象哈希复用大文件的条件，覆盖率尚未统计 |
| LFS 加速配置 | 抽查的仓库未配置 `lfs.url`，检查的候选路径未发现 `.gitlfscache` | 尚未证实这些仓库能通过 UGit 缓存服务下载 |

这些观察不代表候选工程的所有仓库、历史和资源均完整，也没有测量节省的时间或流量。源目录与目标分支可以不同，匹配条件以仓库身份和可用对象为准。

**UGit 能复用什么。** UGit 官方说明支持本地 LFS Cache 加速服务，以及 Git LFS 缓存加速。它适合解决资源等大文件的重复下载。安装 UGit 后，还需要对应仓库支持的缓存服务、有效配置和访问权限，普通 Git 命令才可能通过正确配置使用该服务。[UGit 官方说明](https://ugit.qq.com/zh/)

本机 5.54.0 安装包的相关实现中，可以观察到 `.gitlfscache` 配置读取、LFS 服务地址配置和 P2P 下载组件。这只能说明该版本包含这些机制；它不构成稳定的第三方调用接口承诺。本方案不依赖解析 UGit 的私有数据库或直接操作其内部缓存目录。P2P 接入需要后续单独验证版本兼容性、网络条件及下载校验，第一版不自动开启。

**需要区分的数据类型。** 不同数据有不同的复用规则，不能统一用一个“复制缓存目录”操作处理。

| 数据类型 | 复用方式 | 边界 |
|---|---|---|
| Git 提交、树和普通文件对象 | 使用有效本地仓库作为 clone reference | 从真正的远端获取目标分支；完成后解除对源仓库的依赖 |
| Git LFS 大文件 | 按目标提交中的对象哈希复制并校验本地缓存 | 缺失对象通过配置好的服务下载；不能只凭工作区文件名判断一致 |
| Setup 下载的依赖包 | 按依赖清单中的版本、校验值和明确目录复用 | 不同分支的依赖版本可能不同；无可靠校验依据时不自动复用 |
| 工作区中的未提交修改、未跟踪文件 | 自动复用模式不导入 | 源工程可以有本地文件修改，目标工作区仍以远端目标提交为准 |
| SLN、CMake 缓存及编译中间文件 | 在目标目录重新生成 | 可能包含源工程的绝对路径及旧编译配置 |

**界面和配置建议。** 在“管理方案”中增加“初始化加速”配置区域，与工程根目录、分支组一起保存。增加“扫描本地工程”和“查看初始化计划”入口；“同步所选”沿用当前入口。

| 配置项 | 建议值或选项 | 行为 |
|---|---|---|
| 初始化方式 | 自动复用本地工程 / 指定源工程 / 纯网络下载 | 前两种方式都通过 Git/LFS 数据创建目标工程 |
| 本地工程来源 | 可编辑、有优先级的目录列表 | 本机可预填 `D:\MiniGame`、`D:\AIMiniGame`、`D:\MiniGameProfiler` |
| 每仓库来源 | 自动选择 / 指定源仓库目录 | 可以为 AssetRuntime、Source 等分别指定来源 |
| 复用 Git 数据 | 新方案默认开启 | 只作用于新建仓库 |
| 复用 LFS 大文件 | 新方案默认开启 | 先检查目标版本需要的对象，再复用存在且校验通过的对象 |
| UGit/LFS 缓存加速 | 默认关闭；检测到可用配置后可选 | 仅当前下载流程使用，经验证后才允许作为自动回退链的一环 |
| 复用 Setup 依赖包 | 后续阶段可选 | 按依赖清单复用，第一版不提供无校验的目录复制 |
| 无法复用时 | 回退远端下载 / 停止该仓库 | 默认回退；显示失败来源及回退原因 |

新方案可以默认启用本地复用；已有方案缺少新字段时保持原有网络克隆行为，用户开启后再保存，避免升级工具后静默改变执行策略。旧配置导入、方案复制和导出需要覆盖这些字段。

“指定源工程”仍允许按仓库覆盖来源。指定目录无效时，根据回退配置处理，不静默改用另一套未列入配置的工程。“纯网络下载”关闭本次初始化的本地复用和可选缓存加速，使用方案的原始远端与 LFS 配置。

初始化计划按仓库展示以下信息：

- 仓库名称、目标目录、目标分支。
- 选中的源仓库、匹配依据、Git 数据是否可复用。
- LFS 缓存位置与可用状态；拿到目标提交后再补充需要和命中的对象数。
- 预计执行方式、是否需要网络访问、无法复用的原因。
- 目标目录占用、浅克隆、仓库损坏、真实子模块或目录布局冲突等检查结果。

扫描只读取本地信息，不执行 fetch、切分支或修改配置。默认检查用户配置的工程根目录及方案里的仓库相对路径；额外搜索 D 盘其他目录应由“添加来源”或显式扫描范围控制，不在每次启动时递归扫描整个磁盘。

**源仓库选择规则。** 按远端仓库身份匹配，校验实际 Git 根目录、对象目录和仓库格式。不能仅凭 `MiniGame`、`Source` 等文件夹名称匹配，也不能把 Git 向上找到的父仓库误认为当前目录的仓库。

同一仓库可有多个候选来源，先排除无效、损坏及第一版不支持的浅克隆/不完整对象来源，再按用户指定和来源列表顺序选择。SSH 与 HTTPS 地址只有在主机、命名空间、仓库路径等条件能够确认一致时才合并识别；主机别名和地址迁移应由明确映射配置处理。

普通 `.git` 目录、worktree 和 gitfile 都通过 Git 查询真实目录。LFS 存储位置也要读取实际配置，不能硬编码为 `<工作区>/.git/lfs`。源仓库只提供已存在的数据，不在源仓库切分支、fetch、清理或更新配置。源工作区有未提交文件修改不构成对象复用失败；源对象库正在维护或不可稳定读取时，放弃该来源并按配置回退。

**新建仓库的执行流程。** 已存在的有效目标仓库继续走现有同步规则，初始化加速不覆盖现有工程，也不借机丢弃目标工程中的修改。

1. 重新检查目标目录、目标仓库身份和已选择的源仓库。只有不存在或符合当前空目录规则的目标才进入新建流程；非空且不完整的仓库目录继续显示需要处理。
2. 在本次运行专属的临时目录中准备 Git 仓库。使用原始远端、目标分支、`--reference-if-able` 和 `--dissociate`，先避免自动检出触发 LFS 下载。没有可用来源时执行普通网络克隆。
3. 从真正的远端取得本次要检出的目标提交，并固定该提交。Git 数据准备完毕后，确认新仓库不再依赖源仓库的 alternates。源工程随后被删除或清理，不应影响新工程。
4. 根据固定目标提交生成 LFS 对象清单，查询候选来源的实际 LFS 存储目录。按对象哈希和预期大小复制到目标自己的存储中，进行完整性校验；不直接覆盖源缓存，也不为多个工程建立永久共用、可互相清理的缓存目录。
5. 对仍缺失的 LFS 对象，优先使用用户启用且验证过的加速服务；不可用时按规则回退原始 LFS 服务。缓存地址只在当前下载子进程生效，保留原始远端与后续正常访问配置。
6. 检出目标提交并填充 LFS 文件。验证分支、提交、远端、对象独立性及所需 LFS 内容；不能把仍缺少资源的工程标为完成。
7. 验证目标路径仍可接收本次结果后，将临时结果就位，记录所用来源、实际复制量、下载结果和最终提交。嵌套仓库沿用当前配置顺序处理；如果目标路径已被另一操作占用，只报告该仓库的具体冲突。
8. 按原有方案配置进入后续流程：同步后自动准备仍只执行既有构建设置；生成 SLN 和 IB 编译继续由“编译构建”窗口中的选择决定。

Git 官方定义了 reference 复用本地对象、dissociate 在完成后复制必要对象并解除借用关系的行为。它减少网络传输，但仍需要本地复制、整理和检出，目标工程也需要独立磁盘空间；本方案不预设固定加速倍数。[Git clone 官方文档](https://git-scm.com/docs/git-clone)

LFS 对象复用必须发生在自动下载之前。`git lfs checkout` 可以用本地已存在的对象填充工作目录，本身不负责下载，因此应把“填充本地对象”“获取缺失对象”“检出实际文件”分开记录。[Git LFS checkout 官方文档](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-checkout.adoc)

Git LFS 支持通过 `lfs.storage` 指定存储位置，其官方文档也提醒多个仓库共用存储时不要随意执行 prune。因此第一版使用各目标仓库自己的 LFS 存储，复用以复制并校验为主。[Git LFS 配置说明](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-config.adoc)

**队列、目录和失败处理。** 保持各所选仓库独立执行。父仓库失败、脏工作区或找不到本地来源，不成为子仓库的“等待前置仓库”条件；实际目录重叠、路径占用和目标版本中的仓库布局冲突仍按具体原因报告。

目标版本中声明为真正 Git submodule 的目录继续沿用当前工具的识别和处理边界。第一版不将其展平成独立仓库，也不因为发现可用本地源就覆盖父仓库记录的子模块布局。自动初始化子模块如需支持，应作为独立功能设计。（2026-09-30 更新：工具已改为把方案中配置、且路径被父仓库登记为 gitlink 的仓库按独立仓库克隆和更新，不修改父仓库的 gitlink；初始化加速同样适用。见使用说明“各状态如何处理”。）

| 情况 | 建议行为 |
|---|---|
| 无匹配来源、来源无效或仅有不受支持的浅克隆 | 按配置回退网络下载，或停止该仓库；保留原因 |
| 来源在复用过程中被外部维护，借用对象失效 | 终止本次尝试；验证临时目录归属后重新准备，最多回退网络重试一次 |
| 本地 LFS 对象缺失或校验失败 | 不使用该对象；尝试其他已配置来源或下载缺失对象，不修改源工程 |
| UGit/LFS 缓存不可达或不支持该仓库 | 保留错误，按配置改用原始服务；不把安装了 UGit 视为服务可用 |
| 原始远端无权限、目标分支不存在 | 报告失败，不把旧的本地内容伪装成远端最新版本 |
| 磁盘不足、目标目录被占用、路径布局冲突 | 停止该仓库并给出实际路径及原因，不以网络重试代替处理 |
| 停止队列 | 完成或结束当前操作后，不启动下一仓库 |
| 中断当前操作 | 中断本次子进程树，保留失败阶段和临时目录记录；不影响来源目录 |

临时目录与目标目录必须有明确归属记录；删除或移动前检查解析后的绝对路径仍在本次允许范围内。重试只能处理本次创建的临时结果，不递归删除已有工程。第一版不承诺普通 Git 克隆在中断后的字节级续传；能复用已校验 LFS 对象与否，应通过运行记录和实际文件状态判断。

进度显示使用“检查来源 → 复用 Git 数据 → 复用 LFS → 下载缺失数据 → 检出 → 验证完成”。LFS 可以报告实际复制的对象数和字节数；Git 部分按命令进度展示，不能把目录大小当作准确的网络节省量。日志保留来源路径、回退原因和阶段耗时，不输出凭据。

**完整复制工程再更新的定位。** 这条路径可以保留大量已下载依赖和 Git 未管理的资源，但也会复制旧配置、未提交修改、未跟踪文件和构建产物，并需要处理 gitfile、worktree、子模块路径及源目录并发写入。因此先作为后续高级模式，不纳入第一版自动策略。

| 方式 | 主要收益 | 主要成本 |
|---|---|---|
| 复用 Git/LFS 数据后生成目标工程 | 减少重复下载，支持按仓库混合来源，工作区内容对应目标提交 | 本地对象复制、整理和文件检出仍需时间 |
| 完整复制工程再更新 | 能连同部分依赖、未跟踪资源一起复制 | 要明确哪些本地修改和文件允许继承，并检查路径与仓库元数据 |
| 纯网络下载 | 来源与流程最简单 | 已有数据仍可能重复下载 |

如果后续实现完整复制，应为其单独展示复制内容和源工程状态，不自动继承已有“强制更新（不备份）”选项去清理复制结果。SLN、CMake 缓存和编译中间文件默认重新生成；Setup 依赖优先采用明确的版本与校验值规则。

**建议分阶段交付。** 各阶段都保留原有同步、停止、日志和配置能力。

| 阶段 | 交付内容 | 范围 |
|---|---|---|
| 第一版 | 自动/指定来源、逐仓库匹配、Git reference+dissociate、LFS 本地对象复用、网络回退、计划预览和日志 | 优先利用本机已有工程；不要求安装 UGit |
| 第二阶段 | UGit/LFS 缓存配置识别、受支持下载通道验证与回退 | 安装检测与“加速服务可用”分别展示；P2P 需单独验收 |
| 后续可选 | Setup 依赖包复用、完整目录复制模式 | 根据实际依赖清单、布局和复制需求再实现 |

**实现验收要点。** 以下是未来实现时的验收要求，本次文档工作没有执行这些场景。

1. 同源不同分支的仓库可复用；源工程的未提交修改和本地分支不改变目标工作区内容。
2. 目标完成后移走源仓库，目标 Git 和所需 LFS 文件仍可正常使用；目标没有遗留源仓库 alternates 依赖。
3. 不同源工程可为同一方案的不同仓库提供数据；父仓库失败不阻止独立、可执行的子仓库。
4. 父仓库误识别、无效 `.git`、浅克隆、真实子模块、gitfile/worktree 和嵌套目录冲突均有明确结果。
5. 已有且有效的 LFS 对象不会重复下载；缺失、损坏对象被正确补齐；校验失败不污染源缓存。
6. UGit 未安装、只安装组件但无服务、缓存不可达、原始服务认证失败均能区分，不误报成功。
7. 中文和空格路径、磁盘不足、目标被占用、中断及重试不会覆盖已有工程或删除非本次临时目录。
8. 旧配置行为保持兼容，新配置可保存、复制、导入与导出；进度与运行结果对应实际执行阶段。

实现验证优先使用临时 Git/LFS 测试仓库；真实 MiniGame 工程的复制、同步和下载应在对应执行任务中明确选择目标后进行。

## 第一版实现情况

2026-09-30 实现第一版，代码位于 `src/repo_tool/acceleration.py`，由 `service.py` 的克隆分支调用；操作说明见[使用说明 · 初始化加速](usage.md#初始化加速)，结构见[设计文档](design.md)。

**与方案一致的部分。** 自动 / 指定 / 纯网络三种方式、有优先级的来源列表、仓库级来源、Git 与 LFS 复用开关、回退或停止；旧方案默认纯网络，新方案默认自动复用并预填本机存在的三个目录。来源按远端身份和真实 Git 根目录匹配，排除父仓库误识别、浅克隆、部分克隆、正在维护的对象库。执行流程为临时目录中的 `--no-checkout --reference-if-able --dissociate` 克隆、固定目标提交、按对象哈希复制并校验 LFS、补齐下载、检出、验证后就位；每个仓库独立执行，父仓库失败不阻止子仓库。

**实现时确定的细节。**

| 事项 | 第一版做法 |
|---|---|
| 入口 | 主窗口操作栏“初始化计划”；“管理方案”中“扫描本地工程”。均只读，持运行锁 |

**验收要点对照。** 第 1、2、3、4、5、8 项有自动化测试（`tests/test_acceleration.py`、`tests/test_acceleration_ui.py`，使用临时 Git/LFS 仓库和本地文件远端）。第 7 项覆盖中文与空格路径、就位前目标被占用、中断和失败后的临时目录清理；磁盘不足只做了错误分类，没有实际测试。第 6 项属于第二阶段（UGit）。

**只读核对真实来源。** 以默认方案、草稿区中不存在的根目录执行初始化计划（不 fetch、不写任何工程），结果与上文本机观察一致：`D:\MiniGame\AssetRuntime` 因 Git 向上识别到 `D:/MiniGame` 被排除，AssetRuntime 选用 `D:\AIMiniGame\AssetRuntime`；Profiler 的 CommonResource 因浅克隆被排除，CommonResource 与 Editor 没有可用来源；其余仓库以 `D:\MiniGame` 下的仓库为首选。8 个仓库扫描约 19 秒。

**观察到的环境问题。** 本机 Git 2.45.1 在 `git clone` 检出阶段遇到 git-lfs 安装的 post-checkout hook 时会报 “active post-checkout hook found during git clone” 并中止检出（2.45.2 已修复）。加速流程先无检出克隆、再单独检出，不受影响；纯网络方式沿用原克隆命令，LFS 仓库在此 Git 版本上可能遇到该问题，建议升级 Git。
